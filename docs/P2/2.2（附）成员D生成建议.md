## 2. 项目背景与约束分析

### 2.1 项目摘要

校园互助服务平台是一款面向高校在校学生的 Web 应用，核心业务为"需求发布 → 接单 → 执行 → 确认 → 评价"的互助交易闭环，辅以实时消息、信用评价、积分激励及管理员治理功能。

### 2.2 关键约束

| 类别               | 约束                                     | 对架构的影响                                     |
| ------------------ | ---------------------------------------- | ------------------------------------------------ |
| **团队**     | 3 名大二本科生，10 周开发周期            | 禁止选择学习曲线陡峭的架构；架构必须支持并行开发 |
| **规模**     | 500 并发用户，50 req/min 峰值            | 不需要分布式架构；单体即可满足性能要求           |
| **功能**     | 含实时消息（WebSocket）                  | 后端需支持长连接，纯 Serverless 不适用           |
| **部署**     | 校内服务器或合规云服务                   | 部署复杂度不能高，优先单一部署单元               |
| **安全**     | 个人信息保护法合规，防 XSS/SQL 注入/CSRF | 架构需内建安全层，不能依赖外部网关               |
| **外部依赖** | SSO 认证接口、第三方地图 API             | 需设计降级策略和接口抽象层                       |
| **前端**     | 响应式 Web，适配手机浏览器               | 前端框架需支持移动端适配                         |

### 2.3 团队能力假设

基于大二软件工程专业典型课程进度，合理假设团队具备：

- **已掌握**：至少一门 OOP 语言（Java/Python/JavaScript）、基础 SQL、HTML/CSS、基础 Git
- **正在学习**：软件工程方法学、Web 开发基础、数据库原理
- **未掌握**：容器编排（K8s）、消息队列（RabbitMQ/Kafka）、API 网关、服务网格、CI/CD 流水线

> **架构设计的首要原则：匹配团队能力。** 最好的架构不是最先进的技术栈，而是团队能在规定时间内高质量交付的架构。

## 3. 候选架构方案分析

### 3.1 方案 A：前后端分离 + 分层模块化单体（推荐方案）

#### 3.1.1 架构描述

```
┌──────────────────────────────────────────────────────────┐
```

#### 3.1.2 核心特征

| 维度               | 说明                                                                             |
| ------------------ | -------------------------------------------------------------------------------- |
| **部署单元** | 1 个前端静态资源 + 1 个后端服务进程 = 2 个部署单元                               |
| **模块边界** | 后端按业务领域分为 7 个模块，模块间仅通过 Service 接口调用                       |
| **通信方式** | 前端↔后端：RESTful API (JSON) + WebSocket；模块间：同步方法调用 + 内部事件总线  |
| **数据管理** | 共享数据库，每个模块拥有独立的 Repository 层；禁止跨模块直接访问其他模块的数据表 |
| **实时能力** | WebSocket 连接管理器内嵌于后端进程，无需独立消息中间件                           |

#### 3.1.3 优势

1. **学习曲线平缓**：分层架构是大二软件工程课程的标准教学内容。Controller-Service-Repository 三层模式与教材高度一致，团队成员可直接应用课堂所学。
2. **支持并行开发**：前后端分离后，3 名成员可分工——1 人负责前端（Vue.js SPA），1 人负责核心业务模块（订单 + 需求），1 人负责支撑模块（用户 + 消息 + 管理后台）。通过预先定义 API 契约（接口文档），前后端可独立开发、联调时集成。
3. **部署运维简单**：单一后端进程，无需容器编排、服务发现、分布式配置等基础设施。一条 `node server.js` 或 `java -jar app.jar` 即可启动。
4. **调试友好**：所有代码在同一进程中，断点调试、堆栈追踪、日志关联无分布式复杂度。对于 10 周的项目周期，调试效率至关重要。
5. **可演进性**：模块内部的高内聚和模块间的接口调用，为未来拆分为微服务保留了可能性。如果未来用户量增长到需要独立部署某个模块，拆分成本可控。
6. **性能充足**：单体架构在 500 并发用户的场景下完全胜任。没有网络调用开销、序列化开销、分布式事务开销。

#### 3.1.4 劣势

1. **单点故障**：后端进程崩溃则全部功能不可用。但对于校园应用的年可用性 99% 目标（允许 87.6 小时/年停机）而言，这不是致命问题。
2. **无法独立扩缩容**：不能针对热点模块（如消息推送）单独扩容。但在 500 并发规模下，这不是瓶颈。
3. **模块边界依赖纪律**：如果没有严格的 Code Review 约束，模块间可能出现非预期的直接数据库访问，导致耦合劣化。

### 3.2 方案 B：微服务架构

#### 3.2.1 架构描述

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ 用户服务  │  │ 需求服务  │  │ 订单服务  │  │ 消息服务  │
│ (独立部署) │  │ (独立部署) │  │ (独立部署) │  │ (独立部署) │
└────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │             │
     └─────────────┼─────────────┼─────────────┘
                   │             │
          ┌────────┴─────────────┴────────┐
          │       API Gateway (网关)       │
          │   路由 │ 认证 │ 限流 │ 聚合    │
          └────────┬──────────────────────┘
                   │
          ┌────────┴────────┐
          │  消息队列 (MQ)   │  ← 异步通信
          └────────┬────────┘
                   │
     ┌─────────────┼─────────────┐
     │             │             │
┌────┴────┐  ┌────┴────┐  ┌────┴────┐
│ 信用服务 │  │ 积分服务 │  │ 管理服务 │
│(独立部署) │  │(独立部署) │  │(独立部署) │
└─────────┘  └─────────┘  └─────────┘
     各服务拥有独立数据库（Database per Service）
```

#### 3.2.2 评估

| 维度                   | 评价                                                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **开发复杂度**   | **极高**。需要处理服务发现、配置中心、分布式事务（Saga）、链路追踪、统一日志采集、容错熔断（Circuit Breaker）、API 网关路由等。仅基础设施搭建就需 2-3 周。 |
| **可维护性**     | **低**（对 3 人团队而言）。一个业务需求（如"发布订单时扣积分"）可能跨越 3 个服务，需要在多个仓库间协调。Bug 定位需要跨服务追踪。                           |
| **可扩展性**     | 最高。可独立扩缩容热点服务，但本项目的并发规模完全不需要。                                                                                                       |
| **性能**         | 反而更低（在低并发下）。网络调用延迟、序列化/反序列化开销、API 网关跳转，使得单次请求的延迟比单体高出 5-10 倍。                                                  |
| **团队学习成本** | **极高**。Docker、K8s、消息队列、服务网格中的每一项都需要数周学习。大二学生通常不具备这些前置知识。                                                        |
| **10 周可行性**  | **不可行**。团队将在基础设施上耗尽时间，无法完成业务功能交付。                                                                                             |

#### 3.2.3 判定

**微服务架构不适用于本项目。** 微服务解决的是"组织规模化"问题（多个团队并行开发不同模块），而非技术问题。一个 3 人团队 + 500 并发用户的系统采用微服务，是典型的"过度工程化"（over-engineering）。Martin Fowler 曾明确指出：*"Don't even consider microservices unless you have a system that's too complex to manage as a monolith."* 本项目远未达到该阈值。

### 3.3 方案 C：传统 MVC 单体（服务端渲染）

#### 3.3.1 架构描述

```
┌─────────────────────────────────────────────┐
│         服务端 (单体进程)                     │
│  ┌─────────────────────────────────────┐    │
│  │         View (模板引擎渲染 HTML)       │    │
│  │    Thymeleaf / EJS / Jinja2          │    │
│  ├─────────────────────────────────────┤    │
│  │         Controller                   │    │
│  ├─────────────────────────────────────┤    │
│  │         Model (Service + DAO)        │    │
│  └─────────────────────────────────────┘    │
│                    │                         │
│            ┌───────┴───────┐                │
│            │    Database    │                │
│            └───────────────┘                │
└─────────────────────────────────────────────┘
  优点：简单、部署单一
  缺点：前后端耦合、移动端体验差、无法独立开发
```

#### 3.3.2 评估

| 维度                   | 评价                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------- |
| **开发复杂度**   | 最低。模板引擎渲染，无需前后端分离和 API 设计。                                                           |
| **可维护性**     | 中低。View 与 Controller 耦合，业务逻辑容易泄漏到模板中。长期维护困难。                                   |
| **可扩展性**     | 低。未来扩展为移动 App 或小程序时，后端需全部重写 API 层。                                                |
| **团队学习成本** | 最低。                                                                                                    |
| **10 周可行性**  | 可行。                                                                                                    |
| **移动端体验**   | **差**。服务端渲染的页面在移动端浏览器中体验僵硬，无法实现 SPA 的流畅交互（如消息实时推送无刷新）。 |

#### 3.3.3 判定

**不推荐。** 虽然 MVC 单体架构的简单性有吸引力，但其"移动端体验差"和"未来扩展困难"的缺陷与项目需求矛盾——需求明确要求响应式设计适配手机浏览器、WebSocket 实时消息。传统 MVC 模板渲染难以优雅地实现这些需求。

### 3.4 方案 D：事件驱动架构

#### 3.4.1 架构描述

```
┌──────────┐   event    ┌──────────────┐   event    ┌──────────┐
│ 需求服务  │ ─────────→ │  Event Bus    │ ─────────→ │ 通知服务  │
└──────────┘            │ (Kafka/       │            └──────────┘
                        │  RabbitMQ)    │
┌──────────┐   event    │               │   event    ┌──────────┐
│ 订单服务  │ ─────────→ │               │ ─────────→ │ 信用服务  │
└──────────┘            └──────────────┘            └──────────┘
  所有状态变更通过事件异步传播，服务间零直接调用
```

#### 3.4.2 评估

| 维度                   | 评价                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **开发复杂度**   | 高。事件设计、幂等性处理、最终一致性、事件溯源/回溯、死信队列等都是非平凡的工程挑战。                                        |
| **可维护性**     | 低。事件链路的追踪和调试极为困难。一个"订单完成"事件触发积分更新、信用计算、通知发送、统计更新，其中任何一环失败都难以定位。 |
| **团队学习成本** | 极高。需要理解异步编程、消息可靠性投递、事件版本演进等概念。                                                                 |
| **10 周可行性**  | 不可行。                                                                                                                     |

#### 3.4.3 判定

**不推荐。** 事件驱动架构的核心价值是"解耦"和"异步削峰"——本项目的并发量级不需要削峰，而解耦可以通过模块间的接口抽象实现，不需要引入消息中间件。对于本系统的"订单状态变更→积分转移→信用更新→通知发送"这类强一致性要求的业务流程，同步调用比异步事件更安全、更易理解。

## 5. 综合评估与最终推荐

### 5.1 推荐方案

> **方案 A：前后端分离 + 分层模块化单体架构**

### 5.2 推荐理由

#### 理由一：匹配团队能力，最大化交付成功率

这是最核心的理由。架构评审的黄金法则是：**"团队能交付的架构才是好架构。"** 3 名大二本科生在 10 周内，需要完成从学习到交付的全流程。方案 A 的分层模式（Controller → Service → Repository）与教材高度一致，成员可以将精力集中在业务逻辑实现上，而非与基础设施搏斗。

#### 理由二：以"单体内聚、接口分离"平衡简单与规范

方案 A 并非"粗糙的单体"，而是**有纪律的模块化单体**。7 个业务模块在代码层面物理隔离（独立的包/目录），模块间仅通过 Service 接口调用，禁止跨模块直接访问数据表。这保留了微服务"高内聚、低耦合"的思想精髓，但避免了分布式系统的复杂度。

#### 理由三：支持并行开发，利用团队分工

前后端分离将系统切分为两个可独立开发的子系统——前端 SPA 和后端 API。3 人团队可分配为：

- **成员 A**：前端（Vue.js SPA + 组件开发）
- **成员 B**：后端核心业务（需求模块 + 订单模块 + 积分模块）
- **成员 C**：后端支撑业务（用户模块 + 消息模块 + 管理后台模块 + 信用模块）

通过预先约定的 RESTful API 接口文档（OpenAPI/Swagger），前后端并行推进，在第 6-7 周联调集成。

#### 理由四：性能完全满足需求，无过度设计

系统性能要求：500 并发用户、50 req/min 发布峰值。一个正确实现的单体应用（配合 Redis 缓存热点数据）可以轻松达到 5000+ QPS。方案 A 在此场景下不存在性能瓶颈。**不为不存在的规模设计复杂度**，是成熟架构师的标志。

#### 理由五：内建可演进路径

方案 A 不是"死胡同"架构。模块边界清晰 + 接口调用规范，使得未来任何一个模块需要独立部署时（如消息模块成为独立 WebSocket 服务），拆分的边际成本很低——修改调用方改为 HTTP/RPC 调用即可。这是 Martin Fowler 推荐的 **"Monolith First"** 策略。

### 5.3 不选其他方案的原因

| 方案               | 不选的核心原因                                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 方案 B（微服务）   | 基础设施复杂度远超团队能力和项目需要。属于典型的 over-engineering，10 周内无法交付。                                               |
| 方案 C（传统 MVC） | 服务端渲染无法优雅地支持移动端响应式体验和 WebSocket 实时消息。前后端耦合阻碍并行开发。                                            |
| 方案 D（事件驱动） | 异步编程模型和最终一致性处理的复杂度远超二本本科生能力范围。本项目的核心业务流程（订单状态流转）需要强一致性，事件驱动反而不适用。 |

### 6.2 分层职责说明

| 层                    | 职责                                                                     | 不应做的事                           |
| --------------------- | ------------------------------------------------------------------------ | ------------------------------------ |
| **中间件层**    | 横切关注点：认证鉴权、CORS、限流、请求日志、敏感词过滤、异常统一处理     | 不应包含业务逻辑                     |
| **路由/控制层** | 请求参数校验、调用 Service、组装 HTTP 响应                               | 不应包含业务逻辑、不应直接访问数据库 |
| **业务服务层**  | 核心业务逻辑、事务管理、模块间协调                                       | 不应处理 HTTP 请求/响应细节          |
| **基础设施层**  | 数据库访问（Repository 模式）、外部 API 调用封装、文件存储抽象、定时任务 | 不应包含业务判断                     |
| **数据层**      | 持久化存储、缓存、文件存储                                               | —                                   |

### 6.3 数据流示例：发布悬赏需求（含积分托管）

```
用户点击"发布"
    │
    ▼
[前端] 表单数据校验（标题非空、字数限制）
    │ POST /api/demands  { title, category, description, rewardType, points, ... }
    ▼
[中间件] JWT 认证 → 敏感词过滤 → 限流检查
    │
    ▼
[Controller] 参数验证 → 调用 DemandService.publish()
    │
    ▼
[DemandService]
    ├─ 检查 rewardType 是否为 "points"
    ├─ 调用 PointsService.deduct(userId, points, "PUBLISH_REWARD")  ← 模块间接口调用
    │     └─ PointsRepository 更新积分余额、写入流水记录（事务）
    ├─ 调用 DemandRepository.create(demandData)
    │     └─ INSERT INTO demands ...
    ├─ 调用 NotificationService.notify(userId, "DEMAND_PUBLISHED", ...)
    │     └─ INSERT INTO notifications ... + WebSocket push
    └─ 返回创建的 Demand 对象
    │
    ▼
[Controller] 组装 JSON 响应 → 201 Created
```

> **要点**：整个流程在一个数据库事务中完成（积分扣除 + 需求创建）。分布式架构中需要 Saga 模式处理的事务，在单体内只是一个 `BEGIN...COMMIT`。

#### 7.3.2 模块间内部接口示例

```typescript
// 订单模块调用积分模块的接口契约
interface PointsService {
  /**
   * 扣除积分（发布悬赏时调用）
   * @throws InsufficientPointsException 积分不足
   * @returns 交易记录 ID
   */
  deduct(userId: string, amount: number, reason: string): Promise<string>;

  /**
   * 转移积分（确认完成时调用）
   * 从平台托管账户转给帮助方
   */
  transfer(fromUserId: string, toUserId: string,
           amount: number, orderId: string): Promise<void>;

  /**
   * 返还积分（取消订单时调用）
   */
  refund(userId: string, amount: number, orderId: string): Promise<void>;
}

// 订单模块调用消息模块的接口契约
interface MessageService {
  /**
   * 发送系统通知
   */
  notify(userId: string, type: NotificationType,
         payload: NotificationPayload): Promise<void>;

  /**
   * 在订单进入"进行中"状态时，创建双方私聊通道
   */
  createConversation(orderId: string, userA: string, userB: string): Promise<string>;
}

// 订单模块调用信用模块的接口契约
interface CreditService {
  /**
   * 订单完成后触发信用分重新计算
   */
  recalculate(userId: string): Promise<number>;

  /**
   * 违规扣分（管理员操作）
   */
  penalize(userId: string, points: number, reason: string,
           adminId: string): Promise<void>;
}
```

## 8. 技术选型建议

### 8.1 推荐技术栈

| 层次                 | 推荐方案 A（首选）                                   | 备选方案 B                   | 选择理由                                                                                                                          |
| -------------------- | ---------------------------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **前端框架**   | Vue.js 3 + Vant UI                                   | React 18 + Ant Design Mobile | Vue.js 的中文文档和社区资源极其丰富；Vant UI 专门针对移动端；学习曲线比 React 平缓；模板语法接近课堂所学的 HTML/CSS，上手更快     |
| **前端构建**   | Vite                                                 | Vue CLI / CRA                | 开发服务器秒启动、HMR 极快；大二学生对慢构建的容忍度低                                                                            |
| **后端运行时** | Node.js + Express                                    | Python + FastAPI             | JavaScript 前后端统一语言，减少团队上下文切换；Express 是最成熟的 Node.js 框架，中文教程丰富；WebSocket 支持（socket.io）开箱即用 |
| **后端 ORM**   | Prisma (Node.js)                                     | Sequelize / TypeORM          | 类型安全、自动生成迁移、可视化数据库管理界面（Prisma Studio）——对数据库初学者极为友好                                           |
| **关系数据库** | MySQL 8.0                                            | PostgreSQL 15                | MySQL 是国内高校数据库课程的标准教学数据库；团队成员已有基础；免费、成熟、中文资料丰富                                            |
| **缓存**       | Redis 7                                              | —                           | 用于 JWT 黑名单、热点数据缓存、限流计数器、WebSocket 会话管理                                                                     |
| **实时通信**   | Socket.IO                                            | 原生 WebSocket               | 自动重连、房间机制、降级兼容（不支持的浏览器回退 HTTP 轮询）                                                                      |
| **认证**       | JWT (Access + Refresh Token)                         | Session + Cookie             | 无状态、适合前后端分离；移动端适配友好                                                                                            |
| **文件存储**   | 本地磁盘（MVP）→ 阿里云 OSS（后续）                 | —                           | MVP 阶段用户量小，本地存储零成本；接口抽象后切换云存储只需修改适配器                                                              |
| **反向代理**   | Nginx                                                | Caddy                        | 静态文件服务、HTTPS 终止、WebSocket 代理、负载均衡                                                                                |
| **部署**       | 单机 Docker Compose (3 个容器：Nginx + 后端 + MySQL) | 直接 PM2 进程部署            | Docker 降低环境配置成本（"在我电脑上能跑"问题）；Docker Compose 比 K8s 简单 100 倍                                                |

### 8.2 不推荐的技术选项及原因

| 不推荐              | 原因                                                                                                                        |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Java Spring Boot    | 虽然企业标准，但项目配置复杂（Maven/Gradle + Bean 注入 + JPA），对二本学生学习曲线过陡；10 周内从零学习 Spring 全家桶风险高 |
| GraphQL             | 增加了前端查询的灵活性，但学习成本和后端实现复杂度显著高于 REST；对 MVP 过度                                                |
| MongoDB             | 本项目数据模型高度关系型（用户-订单-评价-积分），关系数据库是自然选择；文档数据库的事务支持较弱                             |
| TypeScript (仅后端) | 如果团队有 TypeScript 经验可用，如果是零基础，先 JavaScript 完成 MVP，后续再渐进迁移                                        |

### 8.3 技术栈总结

```
前端：Vue.js 3 + Vite + Vant UI + Pinia（状态管理）+ Axios（HTTP）+ Socket.IO Client
后端：Node.js + Express + Prisma ORM + Socket.IO + JWT + bcrypt
数据：MySQL 8.0 + Redis 7
部署：Nginx + Docker Compose
```

## 9. 架构决策记录 ADR

### ADR-001：选择前后端分离 + 模块化单体架构

**状态：** 已接受

**背景：**
校园互助服务平台由 3 名大二本科生在 10 周内开发，系统需支持响应式 Web 界面（适配手机浏览器）、实时消息（WebSocket）、500 并发用户。团队需要选择一种能在有限时间和能力约束下完成交付的架构风格。

**决策：**
我们决定采用**前后端分离 + 分层模块化单体架构**。

- 前端：Vue.js 3 SPA，通过 HTTPS RESTful API 和后端通信
- 后端：Node.js + Express 单体进程，内部按业务领域划分为 7 个模块（M-01 至 M-07）
- 实时通信：Socket.IO 内嵌于后端进程
- 数据：共享 MySQL 数据库，通过应用层 Repository 模式隔离数据访问

**理由：**

1. **团队能力匹配**（权重 40%）：分层架构（Controller-Service-Repository）是软件工程课程的标准内容，团队可直接应用。微服务（Docker/K8s/MQ）和事件驱动（异步编程/最终一致性）的学习成本在 10 周内不可接受。
2. **性能满足需求**（权重 25%）：500 并发用户 + 50 req/min 峰值远低于单体架构的瓶颈阈值（通常 5000+ QPS）。分布式架构在此规模下反而增加网络延迟。
3. **开发效率**（权重 20%）：前后端分离支持 3 人并行开发（1 前端 + 2 后端）。单体架构下调试（断点、堆栈追踪、事务管理）的效率是分布式架构的 3-5 倍。
4. **可演进性**（权重 15%）：模块边界的严格纪律（接口调用、禁止跨模块直连数据表）为未来拆分微服务预留了可能性。这与 Martin Fowler 的"Monolith First"策略一致。

**后果：**

- **正面影响：**

  - 团队成员可在第 1 周内理解架构全貌，第 2 周开始编码
  - 调试和问题定位效率高，无分布式追踪的复杂性
  - 部署仅需 3 个 Docker 容器，运维简单
  - API 契约明确，前后端可独立开发测试
- **负面影响：**

  - 单点故障：后端进程崩溃则全站不可用（可通过 PM2 进程守护 + 多实例部署缓解）
  - 无法独立扩容热点模块（500 并发下不需要）
  - 模块边界依赖团队纪律，需要 Code Review 防止耦合劣化
- **需要关注的风险：**

  - WebSocket 连接在单进程下的上限（Node.js 单进程可轻松支持 5000+ 并发 WebSocket 连接，500 用户场景下不是问题）
  - 随着需求迭代，需警惕模块间的循环依赖

**AI 辅助记录：**

- AI 初稿内容摘要：AI 最初建议了"事件驱动微服务"架构，理由是"解耦"和"可扩展性"，但未考虑团队能力和项目规模约束。
- 人工修订内容：将架构调整为模块化单体；增加"10 周可行性"和"团队学习成本"作为核心评估维度；明确给出"不选其他方案"的否定性论证。
- 修订理由：AI 倾向于推荐"先进"的架构模式，但忽视了康威定律和团队能力的现实约束。架构设计的首要服务对象是开发团队，而非技术本身。

### ADR-002：选择 Vue.js 3 作为前端框架

**状态：** 已接受

**背景：**
系统需要响应式 Web 前端，适配手机浏览器。团队 3 人中最多 1 人有前端开发基础。需要在 React、Vue.js 和原生 HTML/CSS/JS 中做出选择。

**决策：**
我们决定采用 **Vue.js 3 + Vite + Vant UI** 作为前端技术栈。

**理由：**

1. **学习曲线**：Vue.js 的模板语法接近原生 HTML，SFC（单文件组件）将 HTML/CSS/JS 组织在一个文件中，对大二学生的认知负担最低。React 的 JSX、Hooks 闭包陷阱、useEffect 依赖数组等概念对初学者不友好。
2. **移动端组件库**：Vant UI 是业界最好的移动端 Vue 组件库之一，提供 Tabbar、List、Form、Uploader、ImagePreview 等移动端常用组件，显著降低 UI 开发成本。
3. **中文生态**：Vue.js 和 Vant UI 均由华人开发者主导，中文文档质量极高，中文社区活跃。对于英语非强项的二本学生，这是巨大的生产力优势。
4. **构建工具**：Vite 的开发服务器启动速度和 HMR 速度远超 Webpack，能显著改善开发体验，减少"等待编译"的无效时间。

**后果：**

- **正面影响：** 团队前端成员可在 1 周内上手并产出原型；Vant UI 组件显著减少 CSS 工作量
- **负面影响：** 团队未来进入 React 主导的企业时需额外学习；部分复杂交互（如地图组件集成）可能需要自定义封装
- **风险：** 如果团队成员之前学过 React，切换成本需要考虑（但二本大二学生通常尚未深入学习任何前端框架）

**AI 辅助记录：**

- AI 初稿内容摘要：AI 推荐了 React + Ant Design，理由是"生态最大、岗位最多"。
- 人工修订内容：将推荐改为 Vue.js 3 + Vant UI；增加"学习曲线"和"中文社区"作为核心考量。
- 修订理由：AI 的市场占有率导向建议忽略了"学习成本"这个项目成功的最关键变量。对于 10 周的学生项目，"能快速上手并完成"远重要于"用业界最流行但更难学的技术"。

### ADR-003：选择 Node.js + Express 作为后端技术栈

**状态：** 已接受

**背景：**
后端需要提供 RESTful API、WebSocket 实时通信、数据库 ORM、JWT 认证、文件上传等能力。团队中有 2 人具备基础的 Java 和 Python 经验。需要在 Java Spring Boot、Python Flask/FastAPI、Node.js Express 中做出选择。

**决策：**
我们决定采用 **Node.js + Express** 作为后端运行时。

**理由：**

1. **前后端语言统一**：前端使用 Vue.js（JavaScript），后端使用 Node.js（JavaScript），整个项目只有一种编程语言。对于大二学生而言，减少语言切换的认知负担，意味着更多精力可以投入业务逻辑实现。
2. **WebSocket 原生支持**：Node.js 的事件循环模型天然适合 WebSocket 长连接。Socket.IO 库是 Node.js 生态最成熟的实时通信方案，中文文档和教程丰富。Java 的 WebSocket 支持（如 Spring WebSocket）配置复杂，Python 的异步 WebSocket（如 FastAPI WebSocket）对初学者概念较多。
3. **JSON 原生亲和**：JavaScript 是 JSON 的原生语言，前后端数据交互无需任何序列化/反序列化配置，`JSON.parse()` 和 `JSON.stringify()` 即用。
4. **Express 学习曲线平缓**：Express 的中间件模型（`app.use()`）直观；路由定义简洁；不需要注解、依赖注入、AOP 等 Java Spring 的概念前置知识。

**后果：**

- **正面影响：** 前后端代码可共享部分 TypeScript 类型定义（如果后续引入）；后端开发人员可以阅读前端代码并参与，反之亦然；npm 生态的 package.json 统一管理
- **负面影响：** Node.js 单线程模型下 CPU 密集型任务（如图片处理）会阻塞事件循环；动态类型语言在大型项目中维护性不如 Java（但本项目规模不构成问题）
- **风险：** callback hell（通过 async/await 解决）；未捕获的异常会崩溃进程（通过 PM2 + process.on('uncaughtException') 缓解）

**AI 辅助记录：**

- AI 初稿内容摘要：AI 推荐了 Python + FastAPI，理由是"类型安全、异步性能好、自动生成 OpenAPI 文档"。
- 人工修订内容：将推荐改为 Node.js + Express；增加"前后端语言统一"作为首要理由；补充了"团队英语能力"对中文文档依赖的考量。
- 修订理由：AI 的技术优劣分析是准确的（FastAPI 确实在类型安全和文档自动生成方面优于 Express），但遗漏了"团队认知负担"这个核心约束——前后端同语言对 3 人学生团队的收益远超类型安全对 API 文档的收益。

### ADR-004：选择 MySQL 作为主数据库，补充 Redis 缓存

**状态：** 已接受

**背景：**
系统需要持久化存储用户、需求、订单、消息、评价、积分流水等数据。数据模型高度关系型（用户 1:N 订单、订单 1:1 评价等）。需要事务支持（积分扣除 + 订单创建在同一事务中）。

**决策：**
我们决定采用 **MySQL 8.0 作为主数据库，Redis 7 作为缓存层**。

**理由：**

1. MySQL 是国内高校数据库课程的标准教学数据库，团队成员已在课堂上学习过 SQL、ER 图设计、事务、索引等概念，可以直接应用。
2. 系统的数据模型具有强关系性（用户→订单→评价→信用分），需要 JOIN 查询和外键约束。关系型数据库是最自然的选择。
3. Redis 用于三个场景：(a) JWT Refresh Token 存储和黑名单；(b) 热点数据缓存（需求列表首页、信用分排行榜）；(c) 限流计数器。Redis 不是必须的（MVP 可用内存存储替代），但加入成本极低，能显著提升性能。
4. PostgreSQL 在功能上更强大（JSONB、全文搜索、窗口函数），但"团队熟悉度"的权重高于"数据库功能丰富度"——MySQL 已足够满足所有需求。

**后果：**

- **正面影响：** 团队可直接应用课堂所学的 SQL 和 ER 设计知识；Prisma ORM + MySQL 的组合提供了类型安全的数据库访问，减少手写 SQL 的错误
- **负面影响：** MySQL 的全文搜索能力弱于 PostgreSQL；如果未来需要地理空间查询（如"附近的订单"），MySQL 8.0 的 Spatial 支持虽可用但不如 PostGIS 成熟
- **风险：** 数据库单点故障——通过定期备份（docker volume backup）和主从复制（后续）缓解

**AI 辅助记录：**

- AI 初稿内容摘要：AI 推荐了 PostgreSQL，理由是"功能强大、JSONB 支持、地理空间查询（PostGIS）"。
- 人工修订内容：将推荐改为 MySQL；保留 PostgreSQL 作为备选；给出"团队熟悉度优先于功能丰富度"的权衡说明。
- 修订理由：AI 的功能对比是准确的，但犯了"最佳工具 ≠ 最合适工具"的错误。对于课程项目，使用课堂上教过的数据库能减少 50% 以上的数据库调试时间——这比 JSONB 或 PostGIS 的未来可能性有价值得多。

## 11. 附录：架构演进路线图

```
Phase 1（当前 MVP，第 1-10 周）
  ┌─────────────────────────────────────────────┐
  │  前后端分离 + 模块化单体 + MySQL + Redis      │
  │  部署：单机 Docker Compose                    │
  │  目标：完成所有 P0 需求和核心 P1 需求          │
  └─────────────────────────────────────────────┘
                        │
                        │ 如果用户量增长到 5000+ DAU
                        ▼
Phase 2（后续版本）
  ┌─────────────────────────────────────────────┐
  │  模块化单体（不变）+ 以下增强：                │
  │  · 后端多实例 + Nginx 负载均衡                │
  │  · Redis Cluster（高可用缓存）                │
  │  · CDN 加速静态资源                           │
  │  · 文件存储迁移至 OSS                         │
  │  部署：Docker Compose → Docker Swarm         │
  └─────────────────────────────────────────────┘
                        │
                        │ 如果特定模块成为瓶颈（如消息推送）
                        ▼
Phase 3（远期）
  ┌─────────────────────────────────────────────┐
  │  拆分策略：                                   │
  │  · 仅拆分成为瓶颈的模块为独立服务               │
  │  · 其他模块保持单体                           │
  │  · 引入 API 网关（Nginx/Kong）做路由          │
  │  原则：渐进式拆分，非大爆炸式重写               │
  └─────────────────────────────────────────────┘
```

> **关键原则：永不为了"未来可能的需要"而增加当前复杂度。** 只有当观测到的性能数据或团队组织变化明确要求架构演进时，才进行拆分。这一原则源自 Martin Fowler 的"Monolith First"和《Building Evolutionary Architectures》的核心思想。
