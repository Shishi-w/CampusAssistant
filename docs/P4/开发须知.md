# 开发须知

## 一、Git 分支策略



### 1\.1 分支模型



采用简化的 Git Flow：3 类分支 \+ 临时 bugfix。



```Plain Text
main
  │
  ├── dev                      ← 开发集成分支（默认上游）
  │    │
  │    ├── feature/xxx         ← 功能开发分支
  │    ├── fix/xxx             ← 修复分支
  │    └── refactor/xxx        ← 重构分支
  │
  └── release/xxx              ← 发布候选（仅在准备演示前创建）
```



|分支|用途|生命周期|直接 commit|合并去向|
|---|---|---|---|---|
|`main`|稳定可运行版本|永久|**禁止**|—|
|`dev`|日常集成|永久|允许（小修改）|`main`（发布时）|
|`feature/\*`|功能开发|功能完成后删除|—|`dev`|
|`fix/\*`|Bug 修复|修复完成后删除|—|`dev`（或 `main` 热修复）|
|`refactor/\*`|非功能重构|重构完成后删除|—|`dev`|



### 1\.2 分支命名规范



所有分支名使用 **小写英文**，单词间用连字符 `\-` 分隔。



```Plain Text
feature/<模块缩写>-<简短描述>    例: feature/auth-jwt-login
                                     feature/demand-filter-sort
                                     feature/order-state-machine

fix/<模块缩写>-<简短描述>        例: fix/order-concurrent-accept
                                     fix/auth-token-expire

refactor/<模块缩写>-<简短描述>   例: refactor/points-strategy-pattern
```



**模块缩写**：auth（认证）、user（用户）、demand（需求）、order（订单）、msg（消息）、credit（信用）、points（积分）、admin（后台）



### 1\.3 分支操作规则



1. **从 ****`dev`**** 拉出新功能分支**，不从 `main` 直接分支

2. **每分支只做一件事**：一个功能 / 一个 Bug / 一次重构

3. **分支生命不超过 3 天**：避免合并冲突累积

4. **合并前必须同步 ****`dev`**：

    ```Bash
    git checkout dev && git pull origin dev
    git checkout feature/xxx && git merge dev  # 解决冲突后再合入
    ```

5. **Force Push 被禁止**（任何分支），由 GitLab 保护分支机制强制

## 二、Commit 信息格式



### 2\.1 格式规范



采用 Conventional Commits：



```Plain Text
<type>(<scope>): <简短描述>

[正文（可选，说明为什么这样改）]

[AI-assisted] 或 [Human-written]
```



**核心规则**：



- 标题行不超过 72 字符

- 使用中文描述（团队全员中文母语）

- 必须以 `\[AI\-assisted\]` 或 `\[Human\-written\]` 结尾（继承自 P0《AI 协作契约》）

    

### 2\.2 type 定义



|type|用途|示例|
|---|---|---|
|`feat`|新功能|`feat\(demand\): 实现需求列表分类筛选与分页`|
|`fix`|Bug 修复|`fix\(order\): 修复并发接单乐观锁更新失败`|
|`refactor`|重构（不改变功能）|`refactor\(points\): if\-else 重构为策略模式`|
|`test`|测试|`test\(order\): 补充接单乐观锁并发测试`|
|`docs`|文档|`docs: 更新 P4 Sprint 任务看板`|
|`chore`|构建/配置/工具|`chore: 配置 GitLab CI 自动测试流水线`|
|`style`|代码格式（不影响逻辑）|`style: 统一 Checkstyle 警告修复`|



### 2\.3 scope 定义



|scope|对应模块|
|---|---|
|`auth`|认证与登录（FR\-U01）|
|`user`|用户资料、隐私（FR\-U02, U03, U04）|
|`demand`|需求发布、浏览、标签（FR\-D01\~D06）|
|`order`|订单、争议（FR\-O01\~O07）|
|`credit`|信用分、评价（FR\-E01\~E05）|
|`points`|积分（FR\-P01\~P04）|
|`msg`|消息、私聊（FR\-N01\~N04）|
|`admin`|管理后台（FR\-A01\~A04）|
|`infra`|基础架构（安全、限流、配置、DB）|
|`ui`|前端页面与组件|
|`ci`|CI/CD 配置|



### 2\.4 示例



```Plain Text
feat(auth): 实现学号登录与 JWT 签发

通过 Spring Security Filter 拦截 /auth/sessions 请求，
校验 studentId+password 后返回 JWT Token。
Token 有效期 2h，过期需重新登录。

[AI-assisted]
```



```Plain Text
fix(order): 修复并发接单乐观锁未生效的 Bug

问题：UPDATE 语句缺少 version = #{oldVersion} 条件，
导致乐观锁形同虚设。加上版本号校验后并发测试通过。

[Human-written]
```



```Plain Text
test(order): 补充订单状态机所有合法转换的单元测试

覆盖 6 个状态 × 允许/禁止的转换组合，共 30 条用例。

[AI-assisted]
```

## 三、Merge 策略



### 3\.1 合并方式



|场景|方式|说明|
|---|---|---|
|feature → dev|**Squash \&amp; Merge**|将功能分支的所有 commit 压缩为 1 个整洁的 commit|
|dev → main|**Merge Commit**（非 squash）|保留 dev 的完整合入历史|
|fix → dev|**Squash \&amp; Merge**|同上|
|hotfix → main|**Merge Commit**|热修复需保留轨迹|



### 3\.2 合并前置条件（强制）



所有合并到 `dev` 或 `main` 的 PR 必须：



1. **GitLab CI 通过**（编译 \+ 代码风格 \+ 单元测试全部绿色）

2. **至少 1 名团队成员 Code Review 通过**

3. **无合并冲突**（必须先从目标分支同步并解决冲突）

4. **功能分支推送到远程**（不要只保留本地）

    

### 3\.3 冲突解决规则



1. **谁的分支谁负责解决冲突**

2. 涉及数据库 Schema 变更的冲突，必须拉上架构负责人（陈一沛）一起确认

3. 解决冲突后**必须重新运行测试**再推送

## 四、代码审查策略



### 4\.1 审查角色



**交叉审查原则**：代码产出者不能作为自己 PR 的唯一审查者。



### 4\.2 审查清单



每个 PR 至少检查以下项目：



#### 通用（所有 PR）



* [ ] 是否存在明显的逻辑错误或边界条件遗漏

* [ ] 是否存在安全漏洞（SQL 注入、XSS、未校验的越权访问）

* [ ] API 接口是否与 `docs/P3/3\.API规范文档\.md` 一致

* [ ] 是否有对应的单元测试（核心模块覆盖率 ≥ 60%）

    

#### AI 生成代码（标注 `\[AI\-assisted\]` 的 commit）



* [ ] AI 生成的算法逻辑是否正确、有没有混淆边界条件

* [ ] 是否处理了参数为空、数值越界、并发冲突等异常情况

* [ ] AI 生成的代码是否与 P3 详细设计一致（不要 AI 自由发挥）

* [ ] 是否存在\&\#34;看起来能用但实际有隐藏 bug\&\#34;的代码

    

#### 手写核心函数（标注 `\[Human\-written\]` 的 commit）



* [ ] 代码注释是否清晰

* [ ] 是否复用已有工具类（不要重复造轮子）

* [ ] 是否符合模块分层规范（Controller 不含业务逻辑，Service 不含 HTTP 操作）

    

### 4\.3 审查流程



```Plain Text
1. 开发者提交 PR（推送到远程 feature 分支后）
2. 自行检查：先在本地跑 mvn test / npm run lint
3. 指派审查者：在 PR 描述中 @ 一名团队成员
4. 审查者反馈：
   - 小问题 → 评论标注 "nitpick"（可选修复）
   - 改进建议 → 评论标注 "suggestion"（建议修复）
   - 必须修复 → 评论标注 "blocker"（不修复不能合并）
5. 开发者修复 blocker 后再次推送
6. 所有 blocker 解决 → 审查者 Approve
7. 开发者自行执行 Squash & Merge
```



### 4\.4 审查时效



|PR 类型|预期审查时间内|
|---|---|
|小型（\&lt; 50 行改动）|4 小时内|
|中型（50\-200 行改动）|12 小时内（第二天中午前）|
|大型（\&gt; 200 行改动）|24 小时内|



**建议拆分为小型 PR**（一次只改一个功能点）以加速审查。

## 五、开发流程（Daily Workflow）



### 5\.1 每日开始



```Bash
git checkout dev && git pull origin dev
git checkout -b feature/<模块>-<功能描述>
```



### 5\.2 开发中



- 定期 commit（每完成一个小改动就 commit）

- Commit 信息按第二章规范填写

- 涉及 AI 辅助的代码必须标注 `\[AI\-assisted\]`

- 手写核心函数加 `@author \[姓名\] \[Human\-written\]` 注释

    

### 5\.3 提交 PR 前



```Bash
# 1. 运行测试
cd backend && mvn clean test
cd frontend && npm run lint

# 2. 同步 dev
git checkout dev && git pull origin dev
git checkout feature/xxx && git merge dev
# 解决冲突（如有）

# 3. 推送
git push origin feature/xxx
```



### 5\.4 合入后清理



```Bash
git branch -d feature/xxx          # 删除本地分支
git push origin --delete feature/xxx  # 删除远程分支（或由 GitLab PR 自动删除）
```

## 六、分支保护规则（GitLab 配置）



以下规则由 GitLab Repository Settings → Protected Branches 强制：



|分支|允许 Push|允许 Merge|要求|
|---|---|---|---|
|`main`|Nobody|Maintainers only|CI 通过 \+ Code Review 通过|
|`dev`|Developers|Maintainers only|CI 通过|
|`feature/\*`|Developers|Developers|无（但 PR 需 Review 后才能合入 dev）|

## 七、团队纪律



1. **不得绕过 Code Review**：即使是\&\#34;小改动\&\#34;也要开 PR（直接 push 到 dev 仅限 README/文档修复）

2. **不得删除远程分支的保护规则**

3. **密码/密钥/Token 不得出现在代码中**：使用 `\.env` 或环境变量（`\.gitignore` 已配置排除 `\.env`）

4. **每阶段手写保底**：每位成员至少提交 2 个 `\[Human\-written\]` 的核心函数（继承自 P0《AI 协作契约》第四条）

## 附录 A：GitLab CI 流水线说明



当前 CI 配置（`\.gitlab\-ci\.yml` \+ `\.gitlab/backend\.yml` \+ `\.gitlab/frontend\.yml`）：



```Plain Text
触发规则：
- 仅当 backend/src/** 变更时触发后端流水线
- 仅当 frontend/** 变更时触发前端流水线

后端流水线步骤（3 步）：
  1. mvn clean compile     → 编译检查
  2. mvn test              → 单元测试
  3. mvn checkstyle:check  → 代码风格检查（Google Java Style，不阻断）

前端流水线步骤（2 步）：
  1. npm ci                → 依赖安装
  2. npm run build         → 构建检查
```



**注意事项**：



- Checkstyle 当前配置 `failsOnError: false`，警告不阻断 CI

- Node\.js 版本锁定为 18（`\.gitlab/frontend\.yml`），本地开发建议 Node 16\+

- Maven 使用 JDK 17（Temurin 发行版）
