| SOLID 原则 | 检查问题 | 原始设计是否违反 | 违反说明（原始版本） | 修正方案（新版） |
|---|---|---|---|---|
| S - 单一职责 | 有没有类承担了过多职责？ | 是 | ① User.login() 混入认证逻辑, User.viewOrders()/viewCreditHistory() 混入查询逻辑, User 同时是实体、认证者、查询入口。<br/>② Demand.filterAndSort() 是批量查询职责，不应由实体承担。<br/>③ PointsTransaction 内含 deduct/transfer/refund/exchange 四种不同业务规则。 | ① 认证→AuthService，查询→OrderQueryService/CreditQueryService，User 只保留个人资料职责。<br/>②filterAndSort() → DemandQueryService。<br/>③ 策略模式：四种操作拆为独立策略类。 |
| O - 开闭原则 | 新增需求类型是否需要修改现有代码？ | 是 | ① PointsTransaction 新增积分操作必须加方法或改枚举分支。<br/>② Demand.filterAndSort() 新增筛选项必须改内部逻辑。<br/>③ Order.transitionState() 新增状态需改switch-case。 | ① 策略模式：新增操作只需加 XxxStrategyimplements IPointsOperation。<br/>②DemandQueryService 封装筛选逻辑，新增筛选项不影响 Demand。<br/>③ 状态机逻辑收在 Order 内部，这点保持原样。 |
| L - 里氏替换 | 子类是否可以替换父类使用？ | 是 | `Admin --> User: Admin 的 viewOrders()` 应查全站订单而非个人订单，语义不一致；且普通 User 无法替代Admin（缺少管控方法）。 | 让 User 和 Admin 成为兄弟而非父子，消除谁替代谁的矛盾。 |
| I - 接口隔离 | 有没有接口太"胖"，包含了不需要的方法？ | 否（原版无接口） | 原版类图没有使用接口，不存在接口过胖问题。但隐含着 Admin 继承 User 被迫拥有 login、updateProfile 等不需要的方法。 | 新版仅保留两个聚焦接口：IMessageSender（只管发送）和 IPointsOperation（只管执行），每个接口只有单一方法，无过胖问题。 |
| D - 依赖倒转 | 高层模块是否直接依赖了低层模块的具体实现？ | 是 | ① Order 直接 new Dispute() 创建争议。<br/>②User.login() 内含数据库查询等基础设施代码。<br/>③Message.send() 直接耦合具体发送机制。<br/>④ 所有关联关系都是具体类→具体类。 | ① Order 依赖 StandardDisputeFactory（虽为具体类，<但创建逻辑已隔离）。<br/>② login() → AuthService，实体不触碰基础设施。<br/>③ Message 依赖 IMessageSender 接口，MessageSenderService 实现。<br/>④PointsTransaction 依赖 IPointsOperation 接口。 |
