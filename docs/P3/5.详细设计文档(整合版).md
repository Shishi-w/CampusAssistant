## 2. 设计模式应用



### **2.1 策略模式（Strategy Pattern）**



#### **2.1.1 定义**



策略模式定义一组算法家族，将每个算法封装到独立的类中，使它们可以互相替换。策略让算法的变化独立于使用算法的客户端。



结构：**Context（上下文）→ Strategy（策略接口）→ ConcreteStrategy（具体策略）**



#### **2.1.2 在本类图中的体现**



**涉及类：**



* `PointsTransaction` — Context 角色，持有策略引用

* `IPointsOperation` — Strategy 接口，定义算法的统一契约

* `DeductStrategy` / `TransferStrategy` / `RefundStrategy` / `ExchangeStrategy` — 四个具体策略

#### **2.1.3 为什么在这里使用？**



积分操作有四种完全不同的业务规则：



| 操作 | 校验规则     | 影响账户数 | 业务约束     |
| -- | -------- | ----- | -------- |
| 扣减 | 余额是否充足   | 1 个   | 不可超过余额   |
| 转账 | 双方状态是否正常 | 2 个   | 单向不可逆    |
| 退款 | 原交易是否存在  | 2 个   | 需关联原订单   |
| 兑换 | 兑换比例是否生效 | 1 个   | 需校验兑换项库存 |



如果用 if-else 堆在 `PointsTransaction` 里，四种规则交织在一起，改扣减逻辑时可能影响转账。策略模式将每种操作隔离到独立类，修改互不干扰，且新增一种积分操作（如"积分过期清零"）只需加一个 `ExpiryClearStrategy` 类，不需要改动现有代码。



#### **2.1.4 如果不使用会怎样？**



所有积分操作写在一个类里：





带来的问题：



- **违背开闭原则**：新增操作必须修改 \`execute()\` 方法，加一个 else-if 分支

- **测试困难**：测试扣减逻辑需要确保不影响转账，测试用例相互耦合

- **代码膨胀**：随着操作增多，\`execute()\` 持续膨胀，难以维护

- **修改风险**：改扣减的余额校验时，不小心动了转账的共用代码



---



### **2.2 简单工厂模式（Simple Factory Pattern）**



#### **2.2.1 定义**



简单工厂模式定义一个工厂类，根据参数返回不同产品或封装产品的创建逻辑。客户端不直接实例化产品对象，而是通过工厂方法获取，从而将"使用"与"创建"分离。



结构：**Client（客户端）→ Factory（工厂）→ Product（产品）**



#### **2.2.2 在本类图中的体现**



**涉及类：**



* `Order` — Client 角色，需要创建 Dispute 但不关心创建细节

* `StandardDisputeFactory` — Factory 角色，封装 Dispute 的创建逻辑

* `Dispute` — Product 角色，被工厂创建的产品

#### **2.2.3 为什么在这里使用？**



Order 和 Dispute 属于不同的生命周期：



- **Order** 关注订单流转（接单→凭证→确认），不应该关心 Dispute 的构造细节

- **Dispute** 的创建有额外的业务约束（校验是否可发起争议、设置默认状态、记录时间戳），这些逻辑放在 Factory 里，Order 不必知道

* 如果未来争议规则变化（例如限制同一订单只能发起一次争议、或者争议需要先通知管理员），只需修改 `StandardDisputeFactory`，Order 代码不变

#### **2.2.4 如果不使用会怎样？**



Order 直接 `new Dispute()`：





带来的问题：



- **代码重复**：如果有多个地方需要创建 Dispute（例如管理员代开争议），初始化逻辑散落各处

- **变更成本高**：如果要给 Dispute 增加一个 \`version\` 字段或 \`deadline\` 字段，所有 \`new Dispute()\` 的地方都要改

- **隐藏业务规则**：创建争议的前置条件（如"已完成订单不能发起争议"）嵌在 Order 的业务方法里，不能被复用



---



### **2.3. 其他模式简要说明**



#### **2.3.1 模板方法模式（Template Method）**



Account 作为抽象基类定义身份骨架（id、studentId、passwordHash 等公共字段），User 和 Admin 继承并扩展差异化行为。虽不是严格意义上的模板方法（没有算法骨架），但体现了"公共部分收敛到基类，差异部分下放子类"的设计思想。



#### **2.3.2 仓储模式（Repository Pattern）**



`OrderQueryService`、`CreditQueryService`、`DemandQueryService` 封装数据查询逻辑，对外提供集合式接口（`findByUserId`、`filterAndSort`），使领域实体不直接接触数据访问层。

# API设计（OpenAPI 3.0）





## 1. 全局规约



### 1.1 基础信息



| 项            | 值                                          |
| ------------ | ------------------------------------------ |
| Base URL（开发） | `https://dev.campus-assistant.local/api`   |
| Base URL（生产） | `https://campus-assistant.example.edu/api` |
| 数据格式         | `application/json; charset=UTF-8`          |
| 时间格式         | ISO-8601（UTC，例 `2026-05-17T10:00:00Z`）     |
| 认证方式         | `Authorization: Bearer <JWT>`              |
| WebSocket    | `wss://<host>/ws/chat`（STOMP 子协议）          |



### 2.2 统一响应结构



所有 HTTP 接口均返回三段式结构（与架构文档 §2.3.3 一致）：

```json
{ "code": 0, "message": "OK", "data": { } }
```



分页返回：

```json
{
  "code": 0, "message": "OK",
  "data": { "list": [], "page": 1, "pageSize": 20, "total": 134, "hasMore": true }
}
```


### 2.3 错误码（5 位）



| 错误码   | HTTP | 含义             |
| ----- | ---- | -------------- |
| 0     | 200  | 成功             |
| 10101 | 401  | 未登录 / Token 无效 |
| 10102 | 401  | SSO 认证失败       |
| 10103 | 403  | 账户已被封禁         |
| 10201 | 403  | 权限不足（非管理员）     |
| 20101 | 400  | 参数校验失败         |
| 20102 | 400  | 内容命中敏感词（NF-15） |
| 20401 | 404  | 资源不存在          |
| 30101 | 404  | 需求不存在          |
| 30102 | 409  | 需求已被接单         |
| 30103 | 403  | 仅待接单状态可编辑 / 下架 |
| 30201 | 404  | 订单不存在          |
| 30202 | 409  | 非法状态转换         |
| 30203 | 403  | 非订单参与方         |
| 40101 | 429  | 打招呼次数超限        |

## 3. WebSocket / STOMP 实时通道


OpenAPI 3.0 不原生支持 WebSocket，故单独说明（对应架构文档 §2.3.5、§2.3.6；需求 FR-N03、CI-02、NF-02、NF-06）。



### 3.1 连接



| 项   | 值                                              |
| --- | ---------------------------------------------- |
| URL | `wss://<host>/ws/chat`                         |
| 子协议 | STOMP 1.2                                      |
| 认证  | CONNECT 帧 Header `Authorization: Bearer <JWT>` |
| 异常  | 断开后客户端按指数退避重连（NF-06：1s → 30s）                  |



### 3.2 STOMP 路由



| 目的地                             | 类型        | 用途                   |
| ------------------------------- | --------- | -------------------- |
| `/topic/chat/{conversationId}`  | SUBSCRIBE | 订阅指定会话的双方消息          |
| `/topic/notifications/{userId}` | SUBSCRIBE | 订阅个人系统通知             |
| `/app/chat.send`                | SEND      | 客户端发送聊天消息            |
| `/user/queue/reply`             | SUBSCRIBE | 服务端定向回执（@SendToUser） |



### 3.3 消息体（STOMP body，JSON）



#### 发送（客户端 → 服务端）

```json
{
  "conversationId": "conv_abc123",
  "content": "你好，我可以去取快递",
  "contentType": "TEXT"
}
```



#### 推送（服务端 → 客户端）


```json
{
  "type": "CHAT_MESSAGE",
  "payload": {
    "id": "msg_001",
    "conversationId": "conv_abc123",
    "senderId": "user_001",
    "content": "你好",
    "contentType": "TEXT",
    "timestamp": "2026-05-17T10:30:00Z"
  }
}
```


`type` 枚举：`CHAT_MESSAGE | NOTIFICATION | SYSTEM`。

## 3. 索引设计说明



| 表名                        | 索引字段                          | 索引类型 | 为什么需要这个索引？                                            |
| ------------------------- | ----------------------------- | ---- | ----------------------------------------------------- |
| **accounts**              | `student_id`                  | 唯一索引 | 登录认证高频查询，必须唯一且极速响应。                                   |
| **users**                 | `account_id`                  | 唯一索引 | 1:1 关联认证表，防止一个 account 绑定多个用户资料。                      |
| **users**                 | `student_id`                  | 唯一索引 | 学号是登录和唯一标识的核心，必须保证全局唯一且支持等值精确查询。                      |
| **users**                 | `nickname`                    | 普通索引 | 支持按昵称搜索用户，提升用户检索体验。                                   |
| **users**                 | `credit_score`                | 普通索引 | 支持按信用分排序或筛选（如高信用用户优先推荐）。                              |
| **admins**                | `account_id`                  | 唯一索引 | 1:1 关联认证表，防止一个 account 绑定多个管理员身份。                     |
| **tags**                  | `name`                        | 唯一索引 | 标签名称必须唯一，且支持按名称精确匹配查询，标签检索核心。                         |
| **locations**             | `latitude`                    | 普通索引 | 支持基于纬度的范围查询（配合经度进行LBS附近需求搜索）。                         |
| **locations**             | `longitude`                   | 普通索引 | 支持基于经度的范围查询。                                          |
| **demands**               | `publisher_id`                | 普通索引 | 查询“我发布的需求”列表，高频外键关联查询。                                |
| **demands**               | `category`                    | 普通索引 | 首页按分类筛选需求，核心业务高频查询条件。                                 |
| **demands**               | `status`                      | 普通索引 | 首页按状态（如进行中、已完成）筛选需求，核心业务高频查询条件。                       |
| **demands**               | `reward_type`                 | 普通索引 | 按奖励类型（积分、免费、自定义）筛选需求。                                 |
| **demands**               | `version`                     | 普通索引 | 乐观锁更新时的条件判断字段，加索引提高更新并发效率。                            |
| **demands**               | `status, created_at`          | 联合索引 | 核心查询：首页需求广场默认展示“待接单”且按“最新发布”排序。避免全表扫描。                |
| **demand\_tags**          | `demand_id`                   | 普通索引 | 查询某需求包含的所有标签，外键关联查询。                                  |
| **demand\_tags**          | `tag_id`                      | 普通索引 | \*\*核心优化！\*\*查询包含某标签的所有需求（标签搜索核心功能）。                  |
| **demand\_tags**          | `demand_id, tag_id`           | 唯一索引 | 防止同一需求重复打上相同标签，保证多对多关联唯一性。                            |
| **orders**                | `demand_id`                   | 唯一索引 | 1需求1订单约束，且需要根据需求反查订单，高频外键关联查询。                        |
| **orders**                | `publisher_id`                | 普通索引 | 冗余字段，用于快速查询“我发布的订单”，避免多表联查。                           |

| **orders**                | `status`                      | 普通索引 | 按订单状态（进行中、待结算等）筛选列表，高频查询条件。                           |

| **orders**                | `publisher_id, status`        | 联合索引 | 支持用户查看“我发布的订单”并按状态筛选。                                 |
| **orders**                | `helper_id, status`           | 联合索引 | 支持用户查看“我接的单”并按状态筛选。                                   |
