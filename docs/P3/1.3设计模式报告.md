# 设计模式应用报告

## 1. 策略模式（Strategy Pattern）

### 1.1 定义

策略模式定义一组算法家族，将每个算法封装到独立的类中，使它们可以互相替换。策略让算法的变化独立于使用算法的客户端。

结构：**Context（上下文）→ Strategy（策略接口）→ ConcreteStrategy（具体策略）**

### 1.2 在本类图中的体现

**涉及类：**

- `PointsTransaction` — Context 角色，持有策略引用
- `IPointsOperation` — Strategy 接口，定义算法的统一契约
- `DeductStrategy` / `TransferStrategy` / `RefundStrategy` / `ExchangeStrategy` — 四个具体策略

**代码示例：**

```java
// 策略接口
interface IPointsOperation {
    void execute(PointsTransaction transaction);
}

// 具体策略：扣减
class DeductStrategy implements IPointsOperation {
    void execute(PointsTransaction tx) {
        // 校验余额 → 扣减积分 → 记录流水
    }
}

// 具体策略：转账
class TransferStrategy implements IPointsOperation {
    void execute(PointsTransaction tx) {
        // 双方校验 → 扣除+增加 → 记录流水
    }
}

// 上下文
class PointsTransaction {
    private IPointsOperation strategy;  // 持有策略引用

    void setStrategy(IPointsOperation s) {
        this.strategy = s;             // 运行时切换策略
    }

    void executeOperation() {
        strategy.execute(this);         // 委托给策略执行
    }
}

// 使用
PointsTransaction tx = new PointsTransaction(...);
tx.setStrategy(new DeductStrategy());
tx.executeOperation();                 // 执行扣减逻辑
```

### 1.3 为什么在这里使用？

积分操作有四种完全不同的业务规则：

| 操作 | 校验规则 | 影响账户数 | 业务约束 |
|------|---------|-----------|---------|
| 扣减 | 余额是否充足 | 1 个 | 不可超过余额 |
| 转账 | 双方状态是否正常 | 2 个 | 单向不可逆 |
| 退款 | 原交易是否存在 | 2 个 | 需关联原订单 |
| 兑换 | 兑换比例是否生效 | 1 个 | 需校验兑换项库存 |

如果用 if-else 堆在 `PointsTransaction` 里，四种规则交织在一起，改扣减逻辑时可能影响转账。策略模式将每种操作隔离到独立类，修改互不干扰，且新增一种积分操作（如"积分过期清零"）只需加一个 `ExpiryClearStrategy` 类，不需要改动现有代码。

### 1.4 如果不使用会怎样？

所有积分操作写在一个类里：

```java
class PointsTransaction {
    PointsType type;  // 枚举：DEDUCT / TRANSFER / REFUND / EXCHANGE

    void execute() {
        if (type == DEDUCT) {
            // 扣减逻辑
        } else if (type == TRANSFER) {
            // 转账逻辑
        } else if (type == REFUND) {
            // 退款逻辑
        } else if (type == EXCHANGE) {
            // 兑换逻辑
        }
    }
}
```

带来的问题：

- **违背开闭原则**：新增操作必须修改 `execute()` 方法，加一个 else-if 分支
- **测试困难**：测试扣减逻辑需要确保不影响转账，测试用例相互耦合
- **代码膨胀**：随着操作增多，`execute()` 持续膨胀，难以维护
- **修改风险**：改扣减的余额校验时，不小心动了转账的共用代码

## 2. 简单工厂模式（Simple Factory Pattern）

### 2.1 定义

简单工厂模式定义一个工厂类，根据参数返回不同产品或封装产品的创建逻辑。客户端不直接实例化产品对象，而是通过工厂方法获取，从而将"使用"与"创建"分离。

结构：**Client（客户端）→ Factory（工厂）→ Product（产品）**

### 2.2 在本类图中的体现

**涉及类：**

- `Order` — Client 角色，需要创建 Dispute 但不关心创建细节
- `StandardDisputeFactory` — Factory 角色，封装 Dispute 的创建逻辑
- `Dispute` — Product 角色，被工厂创建的产品

**代码示例：**

```java
// 工厂
class StandardDisputeFactory {
    Dispute create(String orderId, String initiatorId, String reason) {
        // 创建前校验：同一订单是否已有争议
        // 初始化争议的默认状态、时间戳等
        Dispute dispute = new Dispute();
        dispute.orderId = orderId;
        dispute.initiatorId = initiatorId;
        dispute.reason = reason;
        dispute.status = DisputeStatus.PENDING;
        dispute.createdAt = now();
        return dispute;
    }
}

// 客户端（Order）
class Order {
    void initiateDispute(String reason) {
        Dispute dispute = factory.create(this.id, this.helperId, reason);
        // 使用 Dispute，但不关心它是怎么构造的
        this.status = OrderStatus.DISPUTING;
    }
}
```

### 2.3 为什么在这里使用？

Order 和 Dispute 属于不同的生命周期：

- **Order** 关注订单流转（接单→凭证→确认），不应该关心 Dispute 的构造细节
- **Dispute** 的创建有额外的业务约束（校验是否可发起争议、设置默认状态、记录时间戳），这些逻辑放在 Factory 里，Order 不必知道
- 如果未来争议规则变化（例如限制同一订单只能发起一次争议、或者争议需要先通知管理员），只需修改 `StandardDisputeFactory`，Order 代码不变

### 2.4 如果不使用会怎样？

Order 直接 `new Dispute()`：

```java
class Order {
    Dispute initiateDispute(String reason) {
        Dispute dispute = new Dispute();
        dispute.orderId = this.id;
        dispute.initiatorId = this.helperId;
        dispute.reason = reason;
        dispute.status = DisputeStatus.PENDING;   // 重复的初始化逻辑
        dispute.createdAt = new Date();            // 重复的初始化逻辑
        // ↑ 每次创建争议都要写一遍
        return dispute;
    }
}
```

带来的问题：

- **代码重复**：如果有多个地方需要创建 Dispute（例如管理员代开争议），初始化逻辑散落各处
- **变更成本高**：如果要给 Dispute 增加一个 `version` 字段或 `deadline` 字段，所有 `new Dispute()` 的地方都要改
- **隐藏业务规则**：创建争议的前置条件（如"已完成订单不能发起争议"）嵌在 Order 的业务方法里，不能被复用

## 3. 其他模式简要说明（不太严谨）

### 3.1 模板方法模式（Template Method）

Account 作为抽象基类定义身份骨架（id、studentId、passwordHash 等公共字段），User 和 Admin 继承并扩展差异化行为。虽不是严格意义上的模板方法（没有算法骨架），但体现了"公共部分收敛到基类，差异部分下放子类"的设计思想。

### 3.2 仓储模式（Repository Pattern）

`OrderQueryService`、`CreditQueryService`、`DemandQueryService` 封装数据查询逻辑，对外提供集合式接口（`findByUserId`、`filterAndSort`），使领域实体不直接接触数据访问层。
